# CAP-005 — Revenue overstatement despite successful ETL execution

**Case:** Deliberately engineered, synthetic business-quality incident.

## Observations

| Order | Approved cents | Observed cents | Difference |
| --- | ---: | ---: | ---: |
| X-1 | 1000 (one row) | 2000 (two rows) | +1000 |
| X-2 | 2000 | 2500 | +500 |
| X-3 | 3000 | 3000 | 0 |
| **Total** | **6000** | **7500** | **+1500** |

The customer fixture contains **two rows for C-1**. The order extract includes **20% discount for X-2**, but the observed report reflects the **undiscounted** $25.00 rather than the required $20.00.

## Causal assessment

- A one-to-many customer join **could** duplicate X-1; confirm the actual SQL and lineage before claiming it as the proved root cause.
- Missing discount application **could** explain X-2; inspect deployed transformation logic and inputs before asserting a software implementation defect.
- Job success is not evidence that the output is correct.

## BGSTM reporting decision

**Hold publication of the affected report.** Record the discrepancy with the approved oracle, verify source authority, investigate actual join and pricing logic, correct the defect, and rerun reconciliation. Require keys, amounts and total to match before considering release.

## Test execution

Run `python -m pytest -q tests/test_capstone.py` for the controlled investigation checks. Tests are designed to pass **when defects are correctly detected**, not to accept the observed report as valid.
